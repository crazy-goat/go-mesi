# Changelog

## [0.13.0] - Unreleased

### Added
- RoadRunner `timeout` plugin config option: wires the previously hardcoded 10s value to a Go-duration setting that controls the per-include ESI fetch budget, not worker or incoming-request concurrency. Omitted/empty values keep the historical `10s` default; explicit values must be in `[1s, 24h]` and malformed, zero, negative, sub-second or over-limit values fail plugin initialization instead of silently defaulting. The configured budget also applies to the HTTP client used by `shared_http_client`; unit boundary tests and a slow-include middleware test verify the option reaches fetch behavior (#189)
- Traefik `maxWorkers` plugin config option: caps the token-processing drain pool for ESI jobs within one `mesi.MESIParse` call (one nesting level of one page render), wired from `Config.MaxWorkers int` through `New()`'s fail-loud `resolveMaxWorkers()` into `ServeHTTP`'s `mesi.EsiParserConfig.MaxWorkers` — Go-direct platform, no `mesi/`/`libgomesi/` changes. **Absent → `0` → `runtime.NumCPU()*4` library default**, byte-identical to previous behavior (`ServeHTTP` left it zero; `CreateConfig()` doesn't seed it); explicit `0` has the same documented default contract as Apache #171 / Caddy / nginx #219 / php-ext #211 / CLI #197 (**unlike `maxConcurrentRequests`, 0 is not unlimited**). Plain `int`, no pointer sentinel needed (absent == explicit 0). **Negatives rejected at middleware creation** because the core silently substitutes the default for any `<= 0` without warning (`mesi/parser.go:119-122`); this direct-caller gap is tracked separately as #456. Range `[0, 999999999]`, the transport-derived cap mirrored from libgomesi/Apache/nginx/php-ext/CLI — Caddy's uncapped `strconv.Atoi` is the #452 gap family, not inherited. Out-of-range explicit values fail `New()` naming the option; decimals, non-integers and integer overflow fail the typed config decode. **Scope: one page-render parse/nesting level**; every nested parse creates its own pool with the same cap. Difference from `maxConcurrentRequests`: MaxWorkers limits token-processing goroutines (and therefore flat-page fetch parallelism), whereas maxConcurrentRequests is a separate HTTP-fetch admission semaphore. Functional coverage `servers/traefik/test.sh` Tests 16–18: a four-level nested ESI chain fully renders under caps 2 and 100 with byte-identical bodies (three distinct jobs at each non-leaf level: the next nested page and two marker fragments), plus absent → library default; this is a deterministic correctness assertion, not a timing window, matching Apache #171/nginx #219 (#220)
- Traefik `maxConcurrentRequests` plugin config option: caps the number of concurrent `<esi:include>` HTTP fetches within one page render — one `mesi.MESIParse` call (the admission-control semaphore the core installs only when the value is `> 0`, `mesi/parser.go:78`), i.e. **per page render, NOT Traefik-global**: each concurrent request's own parse builds its own semaphore (4 workers × cap 5 → up to 20 outbound connections — the scope note shared with nginx #214), wired by `ServeHTTP` into `mesi.EsiParserConfig.MaxConcurrentRequests` — Go-direct platform, zero `mesi/`/`libgomesi/` changes (the same shape as `timeout` #187 and `maxResponseSize` #210: `ServeHTTP` builds the struct itself and calls `mesi.MESIParse`, no `ParseJson`, no schema key). Unit: concurrent include fetches; includes queued beyond the cap **wait** for a slot (the admission wait shares the `timeout` deadline, `mesi/fetch.go:140-155`), never dropped. **Absent → `0` → unlimited** — byte-identical to previous behaviour: the `EsiParserConfig` literal in `ServeHTTP` never set the field, so it stayed at its zero value `0`, which the core treats as "unlimited" (no semaphore below 1) — the plugin never calls `mesi.CreateDefaultConfig()`, which never sets this field either (`mesi/config.go:98-110`; unlike `timeout`'s `0`, an explicit `0` here is NOT a failure mode — it is the documented contract). Explicit `0` = the documented "unlimited" value (same contract as Apache `MesiMaxConcurrentRequests 0` #170 / Caddy `max_concurrent_requests 0` / nginx `mesi_max_concurrent_requests 0` #214 / php-ext `max_concurrent_requests 0` #206 / CLI `-max-concurrent-requests 0` #192). **Negatives are rejected at middleware creation** (`New()` fails with an error naming the option): the core would only warn (`max_concurrent_requests_invalid`) and normalize a negative to `0` = unlimited (#329), i.e. a malformed explicit value would silently pass as the documented "unlimited" — the same config-load rejection as every landed sibling (nginx #214 did the same at `nginx -t` despite the core's warn+normalize). Range `[0, 999999999]` — **deviation from the issue's uncapped `int` field sketch** — mirrored locally as `maxMaxConcurrentRequests` because libgomesi's `config.MaxMaxConcurrentRequests` lives in a separate module (the keep-in-sync pattern; the same cap in Apache `MESI_MAX_MAX_CONCURRENT_REQUESTS` `servers/apache/mod_mesi.c:214`, nginx `MESI_MAX_MAX_CONCURRENT_REQUESTS` #214 `ngx_http_mesi_module.c:76`, php-ext `mesi.c:71`, CLI `cli/mesi-cli.go:72`; neither core nor Caddy caps the value — Caddy's uncapped `strconv.Atoi` `servers/caddy/mesi.go:347-355` belongs to the #452 gap family, deliberately not inherited, same reasoning as #187/#210). Type: plain `int` (the issue's proposal, matching `EsiParserConfig.MaxConcurrentRequests` being `int`, `mesi/config.go:33`) — absent `==` explicit `0` value-wise so no `*int`/sentinel is needed (same no-sentinel reasoning #210 documented for `int64`; timeout used `*string` because absent ≠ explicit there); decode-level failures (decimals `1.5`, non-integers `"abc"`, 20-digit overflow) fail traefik's config decode loudly before `New()` — #210's empirical finding, re-verified for this field. **Known core limitation (#453), documented not fixed**: nested `MESIParse` calls (the core's own recursion when a fetched fragment contains further includes, `mesi/parser.go:161-162` — traefik itself parses exactly once per response, `ServeHTTP`) unconditionally replace the inherited semaphore (`parser.go:78-80`; `config.go:67-70` has no nil-guard), so with NESTED includes the effective cap can reach cap × nesting depth; flat pages (the common case) are capped exactly — same treatment as nginx #214's README/features note. Functional coverage `servers/traefik/test.sh` Tests 13–15 against new `Host(mcr3.domain.com)` / `Host(mcr0.domain.com)` routers in `esi-configuration.yml`: cap `3` funnels 20 backend fetches to peak in `[2, 3]` with all 20 fragments still arriving (queued beyond the cap, never dropped; peak ≥ 2 proves multi-slot parallelism), explicit `0` and absent both fan out unthrottled (peak ≥ 4 — the `min(NumCPU*4, 20) ≥ 4` fan-out floor, traefik never sets `MaxWorkers`), observed by a new deterministic peak-concurrency gauge in `servers/test-server` (`/holdpage/{n}/{millis}` page + `/hold` registering into `/track/reset`/`/track/max` BEFORE sleeping — a hard semaphore invariant instead of a wall-clock assertion, the same gauge as Apache #170 / nginx #214): **deviation from a timing-style proof, documented** — and holds are 500 ms (not nginx's 1500 ms) because a 7-wave funnel × hold must stay inside traefik's default `10s` `timeout`, which also bounds the admission wait (the wave-vs-timeout starvation interaction — `ceil(n/cap) × hold > timeout` → trailing includes fail — is documented user-facing in the README's Max Concurrent Requests section and in the test.sh comment) (#215)
- Traefik `maxResponseSize` plugin config option: caps the HTTP response body size of a single `<esi:include>` fetch in **bytes** (the limit is per-SINGLE-include, not per page; an over-limit include fails its fetch and renders the empty `IncludeErrorMarker` / fallback body — fail closed, never truncated), wired by `ServeHTTP` into `mesi.EsiParserConfig.MaxResponseSize` — Go-direct platform, zero `mesi/`/`libgomesi/` changes (the same shape as `timeout` #187: `ServeHTTP` builds the struct itself and calls `mesi.MESIParse`, no `ParseJson`, no schema key). **Absent → `0` → unlimited** — byte-identical to previous behaviour: the `EsiParserConfig` literal in `ServeHTTP` never set the field, so it stayed at its zero value `0`, which the core treats as "no limit" (the limiting branch is `MaxResponseSize > 0`, `mesi/fetch.go:288`) — the plugin never calls `mesi.CreateDefaultConfig()`, whose `10 * 1024 * 1024` (`mesi/config.go:106`) only reaches Go callers of that constructor — **deviation from the issue's "default 10 MB" premise**, the same correction as #169 (libgomesi/Caddy/Apache), #201 (php-ext) and #208 (nginx); the CLI (#186) is the one platform where absent really is 10 MB, precisely because it does use `CreateDefaultConfig()`. Explicit `0` = the documented "unlimited" value (same contract as Caddy `max_response_size 0` / Apache `MesiMaxResponseSize 0` / nginx `mesi_max_response_size 0` #208 / CLI `-max-response-size 0` #186) — **deviation from the issue's "0 → default" AC**: a malformed explicit value is never silently replaced by a default (project rule #1), so `0` is accepted as what it documentably means and negatives are rejected instead of normalized; **documented memory-exhaustion risk**: `0`/absent lets a single include against an unbounded backend exhaust Traefik memory. Range `[0, 9223372036854775806]` (`math.MaxInt64 - 1`) — mirrored locally as `maxMaxResponseSize` because `libgomesi/internal/config.MaxMaxResponseSize` lives in a separate module (the keep-in-sync pattern of the CLI's #186 mirror, Apache `MESI_MAX_MAX_RESPONSE_SIZE` and nginx #208); the core computes `MaxResponseSize + 1` for its `io.LimitReader` (`mesi/fetch.go:290`) and at `math.MaxInt64` that wraps negative so the include would silently render an empty body instead of failing (#448) — stricter than Caddy, whose uncapped `strconv.ParseInt` (`servers/caddy/mesi.go:365-373`) belongs to the #452 gap family and is deliberately not inherited (same reasoning as #187's timeout upper bound vs Caddy's missing ceiling). Validated by `resolveMaxResponseSize()` called from `New() (http.Handler, error)` — the traefik plugin API has no `ParseConfig`, so `New()` is the fail-loud site, mirroring the just-landed `resolveTimeout()` and the `maxDepth` range check in the same file: negatives (`-1`, `-5` — the core's `> 0` check would silently treat them exactly like `0`, i.e. a malformed explicit value would pass as the documented "unlimited") and `9223372036854775807` (= cap+1) fail middleware creation with an error naming `maxResponseSize`; values an `int64` cannot represent (`9223372036854775808`, overflow-ish digit strings) and non-integers (`1.5`, `"abc"`) never reach `New()` — the config decode into the typed field fails first, which also fails middleware creation. **Plain `int64`, no pointer sentinel** — unlike `timeout` (absent → 10 s ≠ explicit `"0s"` → rejected), absent and explicit `0` are value-wise identical on this field (both → `0` → unlimited → byte-identical observable), so no distinction is worth a `*int64`; only negatives are distinguishable from absence (absence is `0`, never negative) and they are rejected — traefik's YAML decode over `CreateConfig()` (which deliberately does not seed the field) cannot mint a negative from absence, and an explicit `maxResponseSize: -5` reaches the struct and is rejected by `New()`. - nginx `mesi_max_workers` directive: caps the size of the token-processing drain pool that processes `<esi:include>` ESI jobs within one `MESIParse` call — one nesting level of one page render (the core spawns `min(MaxWorkers, job count)` goroutines, `mesi/parser.go:118-129`, each processing one include at a time; each nested parse spawns its own pool and inherits the cap), i.e. **per page render, NOT nginx-worker-global**. Unit: drain-pool goroutines. **Distinction from `mesi_max_concurrent_requests` (#214)**: that one bounds concurrent HTTP fetches (an admission semaphore), this one bounds the CPU-side goroutine pool that processes tokens/includes — since each goroutine fetches one include at a time, on a flat page it also caps fetch concurrency at that level, but it additionally bounds token-processing work (`mesi_max_workers 1` serializes token processing — useful for debugging), which the semaphore does not (the issue's pool table verified against the core). **Unset → library default `runtime.NumCPU()*4`** — byte-identical to previous behaviour: the request stays on the legacy positional path, where libgomesi leaves `EsiParserConfig.MaxWorkers` at `0` and the core substitutes `NumCPU()*4` for any value `<= 0` (`mesi/parser.go:119-122`, conditional on `len(esiJobs) > 0`); there is no hidden default anywhere on this path (`mesi.CreateDefaultConfig()` never sets the field — `mesi/config.go:98-110`; the same cross-platform contract as the core's documented "Zero means `runtime.NumCPU()*4`" — `mesi/config.go:45-48` — and Caddy's unset `max_workers`). Explicit `0` = the documented "library default" value (same contract as Apache `MesiMaxWorkers 0` #171 / Caddy `max_workers 0` / php-ext `max_workers` #211 / CLI `-max-workers` #197) and must survive the merge: the unset sentinel stays `NGX_CONF_UNSET` (`-1`, re-installed in `create_loc_conf` because `ngx_pcalloc` zeroes — without it a 0 would masquerade as configured and route every parse through `ParseJson`) so a child location's explicit `mesi_max_workers 0` overrides an inherited cap while unset children inherit it (same `-1`-sentinel rule as Apache `MesiMaxWorkers` and nginx's `mesi_timeout` #184 / `mesi_max_response_size` #208 / `mesi_max_concurrent_requests` #214). **Resolved from the issue's AC "`0` → omitted from JSON (or sent as 0)" to what the landed platforms actually do: an explicit directive — including `0` — is SENT as `{"maxWorkers":N}` (Apache's `build_parse_json_config` renders `maxWorkers` whenever `max_workers != -1`; php-ext renders whenever the key is present), while UNSET omits the key and keeps the legacy positional path; with a current `libgomesi.so` there is no observable difference between explicit `0` and absent (both resolve Go-side to `0` and the core substitutes `NumCPU*4` for both; the only difference is routing — the explicit directive goes through `ParseJson` and warns per request against a stale `libgomesi.so` without that symbol, the same honest answer as #201/#206/#214). **Negatives are rejected at config load** — they never reach the core, where ANY value `<= 0` is substituted with `NumCPU*4` **silently, with no warning at all** (there is no #329-style `max_concurrent_requests_invalid` for `MaxWorkers`; that silent substitution for negatives — affecting direct Go callers, the CLI and Caddy — is the open #456, which this ticket deliberately does NOT fix: one ticket = one PR; nginx's digits-only setter keeps malformed values at `nginx -t` instead of letting them pass as the documented default). Range `[0, 999999999]` — **deviation from the issue's uncapped `ngx_conf_set_num_slot` + `ngx_conf_merge_value(..., 0)` sketch**: `ngx_atoi` has no upper bound (`1000000000` would pass and diverge from every other platform) and a merged literal `0` would route every parse through `ParseJson` while destroying the unset-vs-explicit-0 distinction a child's override needs; the custom setter (the `mesi_max_depth` #180 / `mesi_timeout` #184 / `mesi_max_response_size` #208 / `mesi_max_concurrent_requests` #214 pattern) is digits-only, non-empty, with a per-digit overflow guard against the cap **before** the multiply (no intermediate can ever wrap `ngx_int_t`) — negatives (`-1`), signs (`+1`), decimals (`1.5`), non-integers (`abc`, `3foo`), empty values (`""`), cap+1 (`1000000000`), oversized digit strings, a bare argument-less `mesi_max_workers;` and a repeated directive in the same scope (`"is duplicate"`) all fail `nginx -t` with an EMERG error naming the directive and the offending value (no silent default); explicit `0`/`00` is deliberately ACCEPTED (unlike `mesi_timeout 0` — for this directive 0 IS the documented "library default"). The cap is the #171 transport-derived `999999999` (neither core nor Caddy caps the value — Caddy's bare `strconv.Atoi` gap family is #452-tracked, not inherited here), mirrored as libgomesi `config.MaxMaxWorkers`, Apache `MESI_MAX_MAX_WORKERS`, php-ext and CLI `maxMaxWorkers`. - PHP extension `parse_with_config()` plus the in-memory cache backend: takes an associative `config` array alongside the existing `parse()` arguments and supports `cache_backend` (only `"memory"` is exposed — any other value triggers an `E_WARNING` rather than silently caching nothing), `cache_size` (integer in `[1, 1_000_000]`, rejection-warning outside this range), and `cache_ttl` (integer in `[0, 86_400]` seconds, rejection-warning outside this range). The extension tracks the last completed `InitCache` configuration in process-local state so repeated calls with the same parameters don't wipe the in-memory cache between requests — a fresh `InitCache` build always starts empty, so without this guard every cache hit would silently regress to a miss. A fork-based PHPT asserts the cache dedups `<esi:include>` URLs in-process; a second PHPT asserts every validation path (#226)
- Proxy cache backend CLI flags: `--cache-backend` (memory/redis/memcached), `--cache-size`, `--cache-ttl`, `--cache-redis-addr`, `--cache-redis-password`, `--cache-redis-db`, and `--cache-memcached-servers` wire all three cache backends into the standalone proxy server. Unknown backend values are rejected with a clear error — never silently disables cache (#331)
